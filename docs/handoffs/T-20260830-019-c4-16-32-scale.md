## 关键结论

1. 16 和 32 核的 `lcvex_l2_cluster` 模块级参数化 lint/elaboration 均通过；
   目录位图按预期扩到 16/32 bit，owner 仍为 one-hot。
2. `lcvex_cluster_top` 的 no-FP 合成路径（`COHERENCE_ENABLE=1`, `A64_FP_SIMD=0`）
   在 16/32 核下也通过；资源趋势接近线性/约 2 倍每档：no-FP 时间 5.9s→10.9s→21.5s，
   RSS 285MB→532MB→1.03GB，C++ 文件 31→67→132。
3. 新参数化 synthetic L1 smoke `tb/sv/lcvex_c4_cluster_scale_tb.sv` 在 16/32 核均通过：
   - 16 核：37 个事务、30 个 probe、总周期 755、平均延迟 19 cycles；
   - 32 核：69 个事务、62 个 probe、总周期 1459、平均延迟 19 cycles；
   - 覆盖 ReadShared 全 sharer、Upgrade/ReadUnique 多 sharer 失效、dirty owner 迁移、
     WriteBack、out-of-range fault、reset 后无 stale response。
4. 默认 FP 完整 cluster 在 16 核**未完成**：实测约 32 分 40 秒、RSS 5.55 GB 仍无结束；
   已终止，未伪报通过。32 核默认 FP 因此未启动；这是当前测量窗口/资源下的明确限制。
5. 16/32 核规模趋势退化点主要是 **probe 串行**（全 sharer 失效需 N-1 次串行 probe）
   和 **全局单事务** 吞吐：事务数 2N+5，probe 数 2(N-1)，总周期随 N 线性增长，
   吞吐代理由 8 核 0.0521 tx/cycle 降到 16 核 0.0490、32 核 0.0473。
6. 不宣称 16/32 核功能/架构合规/Linux SMP/A10/Fmax；未启动 Quartus。

### 1. lcvex_l2_cluster lint/elaboration

```text
verilator --lint-only --no-assert --no-timing -Wall -Wno-fatal -Wno-UNUSEDPARAM
  --top-module lcvex_l2_cluster -GCORE_COUNT=<N> -GMEM_LINES=1024
  rtl/lcvex_pkg.sv rtl/lcvex_cluster_pkg.sv rtl/lcvex_l2_cluster.sv
```

- 16：PASS，exit 0，wall 1.091 s，peak RSS 63.5 MB，Verilator 0.292 MB / 3 C++ files。
- 32：PASS，exit 0，wall 1.059 s，peak RSS 63.4 MB，Verilator 0.469 MB / 3 C++ files；
  新增既存 `WIDTHTRUNC`：`dbg_cur_core` 仍为 4 bit，而 `cur_core` 为 5 bit（仅为 debug 口）。

### 2. cluster_top no-FP coherent lint/elaboration

```text
verilator --lint-only --no-assert --no-timing -Wall -Wno-fatal -Wno-UNUSEDPARAM
  --top-module lcvex_cluster_top -GCORE_COUNT=<N> -GCOHERENCE_ENABLE=1 -GA64_FP_SIMD=0
  -f rtl/filelist.f rtl/lcvex_l2_cluster.sv rtl/lcvex_c3_sysctrl.sv
  rtl/lcvex_core_wrap.sv rtl/lcvex_cluster_top.sv
```

- 16：PASS，exit 0，wall 10.928 s，peak RSS 532.4 MB，76.696 MB / 67 C++ files。
- 32：PASS，exit 0，wall 21.450 s，peak RSS 1032.5 MB，153.769 MB / 132 C++ files。
- 既有告警：PINCONNECTEMPTY、WIDTHTRUNC（`lcvex_c3_sysctrl` 状态寄存器 32 位截断；
  32 核时 `dbg_cur_core` 也有 4→5 bit 截断）。这些是观测/控制面位宽限制，不是 lint 阻断。

### 3. 参数化 synthetic L1 smoke（新增 `tb/sv/lcvex_c4_cluster_scale_tb.sv`）

构建：


- 32：PASS，wall 26.284 s，peak RSS 560.8 MB，16 C++ files，Verilator 6.218 MB。

运行：

```text

./build/c4_scale_smoke_32/lcvex_c4_cluster_scale_tb
```

- 16：PASS，0.006 s，17.6 MB；37 tx/30 probes/755 cycles/avg 19 cycles。
- 32：PASS，0.013 s，17.5 MB；69 tx/62 probes/1459 cycles/avg 19 cycles。
- 序列均完成：N 核 ReadShared 建 S 集合；core0 Upgrade 失效 1..N-1 成 M；
  WriteBack；第二条 line N 核 ReadShared；last core ReadUnique 失效 0..N-2 成 M；
  WriteBack；out-of-range fault；reset 后无 stale response。

资源增长趋势：no-FP cluster 的 wall/RSS/C++ 文件数在 8→16→32 每档约 2 倍；
l2_cluster 模块本身几乎不随核数增加构建成本（主要仍是模块常量/位宽变化）。
Smoke 二进制随核数增加 C++ 文件 12→16，生成体积 4.195→6.218 MB。
默认 FP 8→16 已出现明显超线性增长：8 核 347 s/2.76 GB，16 核 32+ min/5.55 GB 未完成。

## 限制与边界

- 本任务未宣称 16/32 核完整功能、Linux SMP、A10/Fmax、架构合规。
- 未启动 Quartus，未做物理签核/时序签核。
- synthetic smoke 使用 synthetic L1 client + BFM，`USE_REAL_CORE=false`；
  不是真实 core 指令级并发，也不是 Linux/多核 OS 验证。
- 默认 FP 16 核未完成、32 核未测；只记录 no-FP/synthetic 路径结果。
- 32 核 cluster_top no-FP lint 通过，但 RTL 仍有已知位宽/可观测性限制：
  - `lcvex_cluster_pkg::CORE_ID_W` 仍为 4（默认），32 核完整 cluster top 使用默认
    `CORE_ID_W=4` 会产生 `dbg_cur_core` 截断告警；
  - `lcvex_c3_sysctrl` 状态寄存器宽度为 32，32 核状态向量会截断；
  - 这是在 C4 规模测量中暴露的后续扩展点，不构成 32 核控制面合规。
- 本任务只新增参数化 synthetic TB；未修改 RTL 功能，未引入 ACE/CHI/SVE/per-bank。
- 所有重型构建均在 cgroup 下串行执行，`VERILATOR_JOBS=1`，未并行重型构建。
