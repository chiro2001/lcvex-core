## 目标

在干净目录重放 `qemu/patches/` 的 12 个 QEMU 11.1.0 fork patch，计算 canonical
combined SHA256，并尝试构建 QEMU 与 difftest 插件；若与 AUD-06 canonical 不一致

## 结论（重要）

1. **Canonical combined SHA256 可复现**：
   `33abdb70e02fbfd40b6fa784302c6f5ff25410960c97958cc1804f6070615c94`，
   与 AUD-06 / EXT-02-001 的一致；12 个单文件 SHA256 也全部一致。
2. **但“干净重放 12 patches 可得到当前 QEMU fork 并可构建”不成立**。
   按仓库现有 `qemu/patches/` 原样应用后：
   - `0012-lcvex-fp-state.patch` 的两个 hunk 都是零上下文（`@@ -N,0 +M,K @@`
     且无实际 context 行）。项目重放脚本 `apply-patches.sh` 使用
     `git apply`；`git apply` 对 0012 的 `qemu-plugin.h` hunk 会把它追加到
     `include/plugins/qemu-plugin.h` 的 `#endif` 之后，而不是像当前 fork 一样
     放在头文件保护内、`qemu_lcvex_difftest_get_cntvct()` 声明之后。
   - 因此原样 fresh replay 的 QEMU 构建在 `plugins/core.c` 编译时报
     `struct qemu_lcvex_fp_state` 重定义（该头文件会被 `qemu/plugin.h` 与
     `plugins/qemu-plugin.h` 两次包含，保护外的声明没有 include guard），
     `ninja` 失败。
   - 补充：用 GNU `patch` 手工应用同一 0012 可以把块放到正确区域附近，但与
     当前 fork 仍差一个空行，且不解决 sidecar v4/timer kick 缺失；规范入口
     是 `git apply`，所以不能视为可复现。
   - 当前 fork 中还包含未收录进这 12 个 patch 的改动：`LCVXSYS4`
     /`CONTEXTIDR_EL1`（T-20260829-097 sidecar v4）以及 `helper.c` 中
     `gt_cntvoff_write`/`gt_cntpoff_write` 的额外 `qemu_cpu_kick()`。
     因此即使手工修正 `0012` 的位置，构建出的树仍与当前 fork 不一致。
3. **判定**：AUD-06 只定义了 patch 文件内容 hash，尚未保证“应用后树 == 当前
   fork/可构建”。本任务暴露 EXT-02-001 的下一层问题：patch 内容 hash 正确，
   但 patch 内容本身不是当前 fork 的完整可重放表示；需要补做 QEMU fork
   状态对账、重新导出/修正 `0012` 以及补录 sidecar v4/定时器 patch
   （或至少把 T-097 的 QEMU fork 改动纳入 patch 管理）。
