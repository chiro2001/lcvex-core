## 结论

T-005 的 acceptance **未满足**，本交付是 diagnostic checkpoint，不能标记为
`done`。在 c141 基线中，F1a FIFO 已保存 current-epoch 取指 fault 的 PC/epoch/seq/FSC，
但 fault head 只有阻止 pop/issue 的路径，没有架构消费，因此稳定出现
`head_fault=1`、`fifo_count=1`、`pop=0` 且后续 160 个周期无 IABT/进展。

动态根因门已完成两种可复现场景：

| 场景 | fault-head 首次签名 | 结果 |
| --- | --- | --- |
| MMU fetch（c141，MEM_DELAY_MODE=2） | `PC=0x44001000, epoch=6, seq=18, FSC=0x07, count=1, pop=0`，cycle 142 | 160 周期无 IABT；更早 cycle 115 已有 older `0x44000ffc` 提交窗口 |
| MMU-off IMEM（默认 reset，4-word image） | `PC=0x00000200, epoch=1, seq=3, FSC=0x10, count=1, pop=0`，cycle 29；先前 standalone reset-PC 变体为 `PC=0x50000000, epoch=0, seq=0` | 160 周期无新的 IABT；`0x5000` 分支的 older IABT 已在 cycle 16 合并 |

先前的 MMU pre-fix d0 记录也稳定观察到 `PC=0x44001000, epoch=6, seq=22,
FSC=0x07, count=1, pop=0`（cycle 52），因此 delay2 checkpoint 的 seq/cycle 差异是
响应延迟造成的，不是根因变化。

## 协议阻断与撤回内容

MMU fault 响应晚于 older 指令提交。现有 QEMU step plugin 要求将取指异常合并到
older pending `PRE/COMMIT`，不能把 fault head 另造一个绕过提交边界的 packet。曾经
短暂试验过 IFID synthetic fault metadata、fault-head ready/hold 和 synthetic
`sys_commit`，post-fix probe 虽产生了 `commit_pc/FAR=0x44001000`、
`EXC_IABORT=0x21`、`ESR=0x86000007`，但 older `0x44000ffc` 已先提交，违反上述
协议；所有实验性 RTL 已用 `apply_patch` 完整撤回，当前 `git diff -- rtl/lcvex_core.sv`
为空。

FIFO-full held fault 的 `+H03_HOLD` 也没有自然 arm：单 outstanding fetch 结构下，
fault response 到达时通常是 `fifo_count=1`，未伪造 `count=2 + fetch_fault_pending`，
因此不对该状态作通过性结论。

当前写集只保留 `tb/sv/lcvex_fetch_fifo_tb.sv` 的 testbench probe：

- 增加 `RESET_PC` 参数透传，扩大 probe memory 到 32768 words，以加载 22528-word
  MMU page-table image；不改变 DUT 接口或 RTL 架构状态。

  每周期输出 fault head 的 PC/epoch/seq/FSC、FIFO count/push/pop、IFID、MEM/WB、
  stall/flush 和 commit exception 字段。
- 没有修改 `rtl/lcvex_core.sv`、`rtl/lcvex_pkg.sv`、MMU/arbiter、SoC memory ABI、
  QEMU/plugin、Cocotb、difftest comparator 或公共 commit packet。
