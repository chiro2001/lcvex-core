# LCVEX 交接文档 091：CRC32/CRC32C 标量指令组

日期：2026-08-25（Asia/Shanghai）
前置：handoff 090（QEMU→Verilator checkpoint 系统状态端口）
分支：`feature/p6-system-reg-shim`

## 触发现场

Linux lite 从 `long-after-wfxt` checkpoint 继续时，在本地提交序号
`1,366,878` 到达：

```text
PC=0xffffffc0801b45b8
insn=0x9ac34c00  crc32x w0, w0, x3
QEMU x0=0xb14249c8
旧 RTL：UDEF（ESR=0x02000000）
```

这属于 ARMv8 CRC extension，不是 MMIO 或 QEMU 特例。QEMU virt
`-cpu max` 已启用该扩展，因此 P6 Linux 路径必须实现完整 B/H/W/X 与
CRC32/CRC32C 两个多项式，不能只修现场的 `crc32x`。

## 实现

- `ALU_CRC`：ALU opcode 扩为 6 bit；`crc32_update` 按反射、LSB-first
  算法逐字节计算。IEEE CRC32 多项式为 `0xedb88320`，Castagnoli CRC32C
  为 `0x82f63b78`。
- decoder 接受 8 个助记符：`crc32{b,h,w,x}` 与
  `crc32c{b,h,w,x}`。B/H/W/X 仅改变 Rm 消耗的低 1/2/4/8 字节；Rd 和
  Rn 始终按 W 寄存器处理，写回高 32 bit 强制清零。
- `a64.py`、编码器反汇编对照和 `hard_crc32` 锁步程序均覆盖 8 种形式，
  并额外覆盖 CRC 结果作为下一条 seed 的相关与 W 写回零扩展。
- 独立 `tb/sv/lcvex_crc_tb.sv` 与 Cocotb ALU 向量采用相同的公开测试
  数据：seed `0xffffffff`，data `0x0123456789abcdef`，两个多项式各 4
  个宽度。

## 验证

```sh
make compile
make sim-sv-crc
make sim-cocotb
python3 sim/difftest/check_encoders.py
bash sim/difftest/run_m2_4b.sh --only hard_crc32
```

验收条件是独立 SV、Cocotb、GNU assembler 编码对照，及 QEMU step 锁步的
无缓存/base 与 I+D L1+L2 两种配置均通过。
